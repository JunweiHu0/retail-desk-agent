## 1. 项目在解决什么问题

传统客服机器人通常只能回答问题。Retail Desk 在对话中调用业务工具，获取客户、订单、商品、规格和支付信息，补充处理请求所需的上下文；也可以根据用户意图发起取消、修改、退货和换货。

对数据的修改不是一句自然语言回复：后端先校验业务条件并生成变更前后预览，用户点击确认后，再通过事务写入数据库，返回执行回执并保存审计记录。

这里“实际数据变更”指本项目的 SQLite 零售沙盒，不连接真实电商、物流或支付网关。退款和邮件按 Benchmark 规则模拟记录。

## 3. 技术架构与业务链路

**浏览器 / Vue → FastAPI → Deep Agents / DeepSeek → RetailService / 官方 RetailTools → SQLite**

选择 Python + FastAPI 的主要原因是可以直接复用 Deep Agents、官方 Retail 工具及类型模型，也便于流式输出工具进度。当前 VPS 用单 worker 和 SQLite，适合团队演示规模，尚未进行生产级并发压测。

典型处理链路：

1. 用户登录，后端把可信客户身份绑定到会话。
2. Agent 理解请求，通过查询工具读取该客户的资料、订单和商品信息。
3. 普通查询直接回复，界面同步展示工具轨迹和业务上下文。
4. 修改请求先在数据副本上校验，生成精确预览，尚不提交。
5. 用户在确认卡片查看前后差异，点击“确认执行”或“取消操作”。
6. 确认时复核客户和订单快照，事务内写入变更、审计与回执。

聊天里的“是”“确认”不能代替确认卡片按钮。已登录会话不会因用户提供另一个邮箱而切换客户。

## 4. 界面功能介绍

### 登录与注册

- 支持邮箱和密码登录、注册新账户、退出登录。
- 页面提供演示客户快捷填入，方便团队体验已有订单。
- 新注册账户没有历史订单或支付方式，不会继承其他客户的数据。
- 密码采用带随机盐的 PBKDF2-SHA256；登录凭证使用 HttpOnly Cookie，线上启用 Secure，并限定 `/retail/` 路径。

### 客服助手

- 多轮对话，登录后使用当前账号身份，无需重复提供邮箱核验。
- 右侧展示客户资料、所属订单和当前上下文。
- 展示查询、计算、变更预览等工具调用及执行轨迹。
- 支持历史咨询恢复、创建新咨询和操作审计查看。
- 涉及修改时展示前后差异与确认卡片，提交后显示实际执行回执。

### 订单管理

- 按订单号或商品名称搜索，按订单状态筛选。
- 查看订单商品、规格、金额、收货地址、付款/退款及物流记录。
- 待处理订单：发起取消、收货地址修改、支付方式修改。
- 已送达订单：按商品选择申请退货及退款方式。
- 商品规格修改、换货等复杂需求可点击“咨询此订单”，将订单上下文带入 Agent。
- 订单页发起的变更会进入同一套客服确认流程，确认后刷新即可看到新状态。

### 个人信息

- 查看姓名、邮箱、客户编号、默认地址和支付方式。
- 发起默认地址变更，仍需预览并确认。
- 修改默认地址不会自动改变已经下单的订单收货地址。

## 5. Benchmark 跑了什么、效果如何

### 评测范围和配置

- 使用当前上游 runner 注册的默认英文 Retail base **完整 114 条任务（ID 0–113）**，每条运行一次。
- 仓库另有 50 条发布筛选集；本次报告的是 114 条完整注册任务，不能混称为那 50 条的分数。
- Agent：Deep Agents + `deepseek-flash`；用户模拟器和自然语言评分器也使用 DeepSeek Flash。
- 两轮均为 seed=42、并发 3、最多 100 步、单任务最多 600 秒，不按失败分数重试。
- 不修改官方任务、业务工具、预期答案或 reward，评测数据与网页沙盒隔离。

### 完整两轮对比

| 指标 | 基线 | 优化后 |
| --- | ---: | ---: |
| 完成任务数 | 114 / 114 | 114 / 114 |
| 通过任务数 | 96 / 114 | 98 / 114 |
| 成功率 | 84.2% | 86.0% |
| 最终数据库状态匹配 | 101 / 114 | 101 / 114 |
| 平均对话执行耗时，不含后置评分 | 26.2 秒 | 23.0 秒 |

净增加 2 条通过，提升约 **1.75 个百分点**。最终仍有 **16 条任务未通过**。13 条任务由失败变为通过，同时有 11 条由通过变为失败，因此结论是小幅净改善，不能描述为全面修复或稳定的大幅提升。

中途还试过两个候选版本，分别在 35 条和 76 条时停止；最终优化版是从头跑完 114 条，成绩没有拼接中途结果。

### 做过哪些优化

- 从真实工具结果推导库存、可用规格、最低价格和订单金额，减少凭空判断。
- 明确同一订单退货与换货的状态冲突，先确定用户处理优先级。
- 保留多订单请求的完整范围，不擅自扩展取消或回退对象。
- 调整地址、支付和一次性商品修改的执行顺序。
- 先按库存、规格和预算筛选可行商品，再比较选项，保留用户未要求改变的规格。
- 尊重用户明确选择的支付或退款方式；修改细节后重新确认。

### 如何解读这个分数

这是根据完整集失败分析后，在同一任务集上的优化回归；**不是独立未见集结果，也不是官方 frozen leaderboard 提交**。成绩属于指定 Agent、模型、用户模拟器及评分配置的组合，不代表所有模型或真实零售场景的通用能力。

网页为了用户可控性增加了按钮确认和账号绑定，与 Benchmark 自动评测适配器的交互方式存在差异；不要把网页演示成功率直接等同于 86.0%。

完整结果、逐任务对比和失败评分理由：[Retail 完整评测报告](https://github.com/JunweiHu0/retail-desk-agent/blob/dev/docs/reports/retail-full-20261027.md)。原始检查点与回归报告在项目中留存。

## 6. 怎么使用线上 Demo

### 第一步：通过团队门禁

打开 **https://junweihu.site/retail/**。

浏览器首次访问可能弹出 HTTP 身份验证框：用户名为 `team`，密码由项目负责人单独提供。完整团队凭据已经保存在负责人电脑的 `retail-agent/.deployment/团队访问凭据.txt`，不写进这篇笔记或 GitHub。

如果网页完全无法连接，先检查当前网络是否能够访问服务器；负责人本机此前需要启用系统代理才能访问该 VPS。门禁返回 401 时，检查输入的是团队门禁凭据，而不是下面的客户登录凭据。

### 第二步：登录演示客户

进入 Retail Desk 登录页后，点击 `li.ming` 快捷填入，再点击“登录工作台”。也可以手动输入：

- 客户邮箱：`li.ming@retail-demo.example.com`
- 合成演示客户密码：`Demo@Retail2026!`

页面也提供 `wang.fang`、`zhang.wei`；内置合成客户的演示密码相同。它们是客户沙盒账户，与浏览器门禁账户是两层不同的验证。

### 第三步：建议的 5 分钟演示路线

1. **个人信息**：查看当前客户姓名、邮箱、默认地址与支付方式，说明这是后端返回的业务上下文。
2. **订单管理**：浏览三笔演示订单，使用状态筛选，打开一笔订单查看商品和支付记录。
3. **Agent 查询**：点击“咨询此订单”，观察自动查询、工具轨迹及返回的订单信息。
4. **展示修改预览**：对仍处于待处理状态的订单发起取消，选“不再需要”，进入客服卡片查看前后差异；如只需展示流程，可以选择“取消操作”。
5. **可选：确认一次变更**：确认后返回订单管理并刷新，展示数据库状态已经改变，以及客服中的执行回执和审计记录。
6. **账号隔离**：退出后登录 `wang.fang`，展示其订单与历史咨询不同。

可直接使用的自然语言请求：

> 请查询订单 #W9000001 的状态和商品明细。

> 请取消订单 #W9000001，原因是不再需要。

> 请把订单 #W9000002 的全部商品退货，退回原支付方式。

上述订单号属于 Ming Li。先在订单页确认当前状态；如果已被其他演示者取消或退货，不应期待它还能按初始状态处理。

### 演示时需要知道的行为

- 团队成员共用线上模拟数据库；同一客户的订单变更会被其他成员看到。
- 订单状态可能已被前面的演示修改。优先换另一位合成客户，服务不会自动重置数据库。
- 修改默认地址、订单取消或退货，必须点击确认卡片才执行。
- 聊天调用真实 DeepSeek，会产生模型 API 用量。仅使用合成客户数据体验。
- 可注册独立账号，但新账户无订单，不适合直接演示售后操作。

## 8. 当前限制与后续建议

以下为建议方向，尚未全部实现：

- 针对剩余 16 条失败任务继续分析状态变更、回答断言和多商品选择，减少修复带来的回退。
- 建立独立留出集与多随机种子重复实验，报告波动，避免只追逐同集分数。
- 为团队展示增加独立演示数据集或可审计的数据重置流程，避免多人相互影响。
- 增加真实使用的耗时、token / 成本、工具错误率与端到端成功率监控。
- 扩大使用前补充整体并发、全局用量配额与生产运维验证；目前定位为团队演示原型。
- 保持桌面 Web 优先；手机端暂不开发。
