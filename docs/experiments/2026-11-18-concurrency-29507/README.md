## 观察

1. **调大 max-num-seqs 确实提吞吐**：req/s 从 0.66（segs=4 时）涨到 1.39，约 **2.1 倍**。
2. **代价是延迟**：TTFT p50 501 ms → 9,266 ms（×18），TPOT 15.65 → 92.5 ms（×6），
   e2e 3.9 s → 28.5 s（×7.4）。
3. **KV 峰值只有 54%，抢占 0 次**。也就是说 40 并发下显存仍然够用——
   瓶颈是算力和批处理调度，不是 KV。
4. 思考关时 tok/s 在并发 10 后就平台化（53 → 57），因为输出只有 25 token，
   批处理摊薄的权重读取很有限，请求开销占主导。

## 一个被推翻的估算

之前我用"KV 池 10.24 GiB ÷ 32,768 上下文"推算出 0.32 MB/token，据此说"KV 只够 5.5 个请求"。
**这个推算错了**：池子容量不等于 32k token 的需求量。实测 40 并发、每请求 5.8k token、
KV 占 54%，反推每 token 约 **27 KB**（这个模型大量层是 mamba，KV 很小），
池子能容纳约 40 万 token。

所以 **KV 不是这套负载的约束**；`max-num-seqs=4` 也不是为了省显存，而是延迟/吞吐的取舍点。

## 选型建议

| 场景 | max-num-seqs |
| --- | --- |
| 单用户交互（agent 对话） | 4 或更低，优先延迟 |
| 批量离线（跑评测、生成数据） | 40，优先吞吐 |
| 多用户在线 | 取决于 SLO：TTFT ≤ 2 s 时约 4–6 |
