## 数据条件复核

- Task 52 原始工具结果：24MP/3x/SD 的原相机没有仅变焦增加的可用同规格替代；预设 item 9228757377 为 30MP/10x/SD。
- Task 105 原始任务 initial_state=null；只读 seed、保存轨迹和上游工具源码均确认差额 21.10 大于余额 17。源码会拒绝余额不足的礼品卡。
- 复核过程中，一次附加的换货调用复现被自动审批拒绝，之后只读检查 JSON 和代码完成核对，没有调用该修改工具或改变业务数据库。

## 候选回归

首次优化候选在 Task 18 允许原规格换原规格。上游工具接受了调用，但 Retail policy 要求不同规格，因此这是需要修复的政策缺口。
候选检查点保存于 `runtime/benchmarks/retail-full-after-20261027/results.json`（35 条）。该候选被停止，新增服务层和适配器同规格校验后，最终版从头跑完整 114 条。

完整集既用于错误分析也用于回归验证，不能把回归提升视为未见任务泛化表现。所有模拟用户/预设冲突保留官方原分，未修改任务、预期答案、官方工具或评分器。

第二候选的 Task 37 暴露了防护过严：模型的计划同时包含要改变的商品和本来已是最低价的未变商品，整单被相同规格校验拒绝，模拟用户因此转为取消。
第二候选在 76 条停止。修正为：有实际变化时仅剔除 old_id==new_id 的无变化项；不改变其他商品、数量、订单或支付方式；纯粹同规格换货仍拒绝。
最终版本以 `retail-full-final-20261027` 从头进行完整 114 条复测。

只读检查还确认上游 `modify_pending_order_items` 在多商品更新循环中复用了前一循环的最后一个 `variant`，可能把多件商品的价格/options 显示成最后一件。此轮未改动上游工具，以免改变评测标准；这类工具异常与 Agent 选错参数分别记录。
